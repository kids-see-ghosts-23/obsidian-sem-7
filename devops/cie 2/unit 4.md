# PART A — RUNNING CONTAINERS

## 1. Containers and Pods

### 1.1 Pods — the basics
- The container is the most fundamental Kubernetes object, but **Pods are how containers are run**.
- **Pod = the unit of scheduling.** Everything that runs in Kubernetes runs by means of a Pod.
- Definition (Hightower et al.): a Pod is a **collection of application containers and volumes running in the same execution environment**.
- **Pods, not containers, are the smallest deployable artifact** in a cluster.
- All containers in a Pod **always land on the same machine (node)**.
- Simple apps → **1 container per Pod**; complex apps → 2 or more.
- "Pod" and "container" are often used interchangeably, but they are not the same thing.

### 1.2 What is a container?
- A **standardised package** containing software + its dependencies, configuration, data — everything it needs to run.
- Linux: everything runs as a **process** (binary + memory state). Normally all processes share one global namespace and can see each other.
- **A container is an isolated process (or group of processes) in its own Linux namespace(s)**:
    - processes inside cannot see outside, and vice versa;
    - it cannot access another container's resources;
    - the boundary is a **ring-fence** around CPU, memory and filesystem.
- From the process's point of view it is running on its **own machine** with all resources to itself.
- Demonstration inside a BusyBox container:
    ```bash
    kubectl run busybox --image busybox:1.28 --rm -it --restart=Never /bin/sh
    / # ps ax
    PID   USER   TIME   COMMAND
      1   root   0:00   /bin/sh
      8   user   0:00   ps ax
    / # hostname
    busybox
    ```
    - `ps ax` normally shows hundreds of processes — here only the shell and `ps` itself.
    - `hostname` returns the container's name, not the host's.
    - Processes run as **root** by default inside the container → relevant to §3.
- (Fun fact: Liz Rice's talk *"What is a Container, Really?"* builds one in Go without Docker.)

### 1.3 Container runtimes
- Docker is **not the only** way to run containers.
- In **December 2020**, Kubernetes maintainers announced the **Docker runtime would be deprecated** in favour of runtimes using the **CRI (Container Runtime Interface)**.
- This does **not** mean:
    - Docker containers stop working in Kubernetes, or
    - Docker stops being useful outside Kubernetes.
- **Any container conforming to OCI (Open Container Initiative) standards runs in Kubernetes** — Docker-built images are OCI-compliant.

> **Exam tip:** remember **CRI** and **OCI**. Docker-built images still work because they are OCI-compliant.

### 1.4 What belongs in a container?
- Technically you can run many processes in one container (even a whole Linux distro) — hence "lightweight VMs" — but you lose the isolation benefit.
- **Rule: a container should do ONE thing.**
- If processes don't need to know about each other, they don't belong in the same container.
- The demo app (listens on a port, returns "Hello, 世界") is self-contained → perfect for its own container.
- **Entrypoint**: the command run at container start; usually creates one main process. To start several separate processes you need a wrapper script.
- Running a large group of unrelated processes in one container means **you are not using containers properly** — split the app into communicating containers.

### 1.5 What belongs in a Pod?
- A Pod = containers that need to **communicate and share data**, so they must be:
    - scheduled together,
    - started and stopped together,
    - run on the same physical node.
- **Example 1 — app + Memcached:** they only talk over a network socket, so two containers in one Pod is ideal; the connection is always local.
- **Example 2 — web server + blog app:** NGINX serves HTML generated by the blog container; they share a disk **Volume**, so NGINX can serve the files over HTTP.
- **Deciding question (Hightower): "Will these containers work correctly if they land on different machines?"**
    - **No → same Pod.**
    - **Yes → separate Pods.**
- 1 container is fine; 2–3 is OK; **more than that → consider splitting into separate Pods**.

| Aspect | Container | Pod |
|:--|:--|:--|
| What it is | Isolated process(es) with own namespace; packaged software | Group of 1+ containers + volumes in the same execution environment |
| Role | Runs the application | Unit of scheduling, smallest deployable artifact |
| Placement | Runs inside a Pod | All containers land on the same node |
| Guideline | Do one thing / one main process | Containers that must work together as one job |

## 2. Container Manifests

### 2.1 Container spec
- Containers are defined in `spec.template.spec.containers` of a Deployment (or `spec.containers` of a Pod).

```yaml
spec:
  containers:
  - name: demo
    image: cloudnatived/demo:hello
    ports:
    - containerPort: 8888
```

```yaml
spec:
  containers:
  - name: container1
    image: example/container1
  - name: container2
    image: example/container2
```

- **Only `name` and `image` are required**:
    - `name` — so other resources can refer to the container;
    - `image` — what to run.

### 2.2 Image identifiers
An image identifier has **four parts**; everything except the image name is optional.

Full example: `docker.io/cloudnatived/demo:hello`

| Part | In example | Explanation |
|:--|:--|:--|
| **Registry hostname** | `docker.io` | Default for Docker images, so usually omitted. Other registries give the hostname (e.g. `gcr.io`). |
| **Repository namespace** | `cloudnatived` | Identifies the owner. If omitted, the default namespace **`library`** is used — official images maintained by Docker, Inc. |
| **Image repository** | `demo` | A particular image in that registry/namespace. |
| **Tag** | `hello` | Different versions of the same image. |

- Popular **library** images: OS bases (`alpine`, `ubuntu`, `debian`, `centos`), languages (`golang`, `python`, `ruby`, `php`, `java`), software (`mongo`, `mysql`, `nginx`, `redis`).
- Common tag styles:
    - **Semantic version** — `v1.3.0` (usually the app version);
    - **Git SHA** — `5ba6bfd…` (the exact commit that built the image);
    - **Environment** — `staging`, `production`.

### 2.3 The `latest` tag
- If no tag is given, Docker defaults to **`latest`**; it is also added automatically when you build/push without a tag.
- `latest` does **not** mean "newest" — it only means "the most recent image that was not explicitly tagged".
- **Always use a specific tag in production** so that deploying tomorrow gives the same image as today.
- OK to omit the tag for **one-off troubleshooting** (e.g. the `alpine` container).
- Kubernetes docs: avoid `latest` in production — harder to know what is running and harder to roll back.

### 2.4 Container digests
- Even a version or Git SHA tag is **not permanent**: a maintainer can push a different image with the same tag → tags are **nondeterministic**.
- A **digest** is a cryptographic hash of the image contents that **immutably** identifies it: many tags, **one digest**.

```
cloudnatived/demo@sha256:aeae1e551a6cbd60bcfd56c3b4ffec732c45b8012b7cb758c6c4a34...
```

### 2.5 Base image tags (Dockerfile)
- `FROM python` means `python:latest` — builds can break when `latest` moves to a version with breaking changes.
- Choose a more specific tag or an exact digest (e.g. `python:3`, `python:3.9`, `python:3.9.7`; also different base OSs).

| | **Less specific** (`python:3`) | **More specific** (`python:3.9.7`) |
|:--|:--|:--|
| Advantage | Auto-pulls updates and security patches on each build | Base image won't change unexpectedly; greater control |
| Disadvantage | Updates may break things (`python:3` silently moving 3.9 → 3.10) | Must manually update the Dockerfile; may lag on security fixes |

- Either way: **check for base-image updates regularly** and have a sustainable rebuild process.

### 2.6 Ports
- `containerPort` declares the port(s) the app listens on; a **Service** can match it to route traffic.

### 2.7 Resource requests and limits (recap Ch. 5)
- Per container: `resources.requests.cpu/memory`, `resources.limits.cpu/memory`.
- A **Pod's** request/limit = **sum of all its containers'** requests/limits.

### 2.8 Image pull policy
| Value | Behaviour |
|:--|:--|
| `Always` | Pull the image **every time** the container starts. With a specific tag this is usually unnecessary — wastes time/bandwidth. |
| `IfNotPresent` (default) | Pull **only if the image is not already on the node**; otherwise reuse the cached image. **Correct for most situations.** |
| `Never` | Never fetch; use the local image or **fail to start**. Rarely wanted. |

> **Troubleshooting tip:** if a Pod isn't updating after you pushed a new image, check `imagePullPolicy`.

### 2.9 Environment variables
- Common but **limited** way to pass runtime information.
- Common because every Linux executable can read environment variables.
- Limited because:
    - values are **strings only** — no arrays, maps or structured data;
    - a process's total environment is capped at **32 KiB**.
- Image-defined `ENV` values are **overridden** by Kubernetes `env` entries.
- For larger/structured/sensitive configuration use **ConfigMaps** and **Secrets** (Ch. 10).

```yaml
containers:
- name: demo
  image: cloudnatived/demo:hello
  env:
  - name: GREETING
    value: "Hello from the environment"
```

## 3. Container Security

### 3.1 Why not run as root?
- Earlier, `ps ax` showed processes running as **root** — the superuser who can read any data, modify any file and perform any operation.
- A full Linux system needs root for some things (`init`), but a container usually does not.
- Running as root violates the **principle of least privilege**: a program should access only what it needs.
- Programs have bugs; some let attackers read secrets or execute arbitrary code → **run with the minimum privileges**.
- Start by assigning an ordinary **non-root user** (no special privileges).
- Attackers can also exploit **runtime bugs to escape the container** and gain host privileges — hence the hardening below.

### 3.2 Running as a non-root user — `runAsUser`
```yaml
securityContext:
  runAsUser: 1000
```
- `runAsUser` is a **UID** (numeric). On most Linux systems **UID 1000+** is the first non-root user.
- The UID **need not exist** in the container — works even on `scratch` images.
- **Precedence**:
    1. `runAsUser` set → overrides the image's user.
    2. No `runAsUser`, image sets a user → runs as that user.
    3. Neither → runs as **root** (bad).
- **Different UIDs per container** = maximum isolation (a compromised container can only touch its own data).
- **Same UID** = needed when containers must **share files** through a volume.

### 3.3 Blocking root — `runAsNonRoot`
```yaml
securityContext:
  runAsNonRoot: true
```
- Kubernetes **checks** whether the container would run as root and **refuses to start it** if so.
- Protects against forgetting to set a user, or third-party images configured for root.
- Symptom: Pod status **`CreateContainerConfigError`**, and `kubectl describe` shows:
    ```
    Error: container has runAsNonRoot and image will run as root
    ```

### 3.4 Read-only filesystem — `readOnlyRootFilesystem`
```yaml
securityContext:
  readOnlyRootFilesystem: true
```
- Prevents the container writing to its own filesystem — it gets an **I/O error** instead.
- Why: a container might exploit a runtime bug so that writes affect **host** files.
- Many containers never write to disk → set it **unless the app really needs to write**.

### 3.5 Disabling privilege escalation — `allowPrivilegeEscalation`
```yaml
securityContext:
  allowPrivilegeEscalation: false
```
- Normally a binary runs with the privileges of the user who executes it.
- **setuid** binaries are the exception: they can temporarily gain the file owner's privileges (usually root) — even if the container runs as UID 1000.
- `allowPrivilegeEscalation: false` blocks this.
- Modern programs use **capabilities** instead of setuid.

### 3.6 Linux capabilities
- Traditional Unix has two levels: **normal** and **superuser** (bypasses all checks).
- **Capabilities** are fine-grained: load kernel modules, raw network I/O, access devices, etc. — grant only what is needed.
- Example: binding to a privileged port (<1024) normally needs root → grant **`NET_BIND_SERVICE`** instead.
- Docker's default set is **generous** (security vs usability trade-off).
- Least privilege: **drop defaults, add only what's required**.

```yaml
securityContext:
  capabilities:
    drop: ["CHOWN", "NET_RAW", "SETPCAP"]
    add: ["NET_ADMIN"]
```

Maximum security:
```yaml
securityContext:
  capabilities:
    drop: ["all"]
    add: ["NET_BIND_SERVICE"]
```

- Capabilities are a **hard limit**, even for root inside the container.
- **Once dropped at container level, a capability cannot be regained**, even by a malicious process with maximum privileges.

### 3.7 Pod-level security contexts
- Some settings can be set at **Pod** level and apply to **all containers** unless overridden per container.

```yaml
spec:
  securityContext:
    runAsUser: 1000
    runAsNonRoot: true
    allowPrivilegeEscalation: false
```

### 3.8 Pod service accounts
- Pods run with the namespace's **default service account** unless told otherwise.
- For extra API permissions: create a **dedicated service account**, bind it to the required **RBAC roles**, and set it on the Pod.

```yaml
spec:
  serviceAccountName: deploy-tool
```

### 3.9 Security settings summary
| Setting | Value | Purpose |
|:--|:--|:--|
| `runAsUser` | UID ≥ 1000 | Run as a specific non-root user; overrides the image user |
| `runAsNonRoot` | `true` | Refuse to start containers that would run as root |
| `readOnlyRootFilesystem` | `true` | Stop writes to the container's own filesystem |
| `allowPrivilegeEscalation` | `false` | Stop setuid binaries from gaining root |
| `capabilities.drop / add` | `["all"]` / `["NET_BIND_SERVICE"]` | Fine-grained least privilege |
| `serviceAccountName` (Pod) | account name | Give the Pod specific API permissions |

## 4. Volumes

### 4.1 Why volumes?
- Each container has its **own filesystem**, visible only to that container, and it is **ephemeral** — data not in the image is lost on restart.
- Often fine (stateless servers like the demo app).
- Complex apps need to **(a) share data between containers in a Pod** and **(b) persist data across restarts** — a **Volume** provides both.
- A Volume mounted on a Pod is **accessible to all containers in the Pod**, whatever the underlying medium.

### 4.2 `emptyDir` volumes
- Simplest type: **ephemeral storage that starts empty**.
- Stored on the **node** (memory or disk).
- Lives only as long as the **Pod runs on that node**.
- Use for: caching downloaded/generated files, scratch workspaces, short-term file sharing between containers.

```yaml
spec:
  volumes:
  - name: cache-volume
    emptyDir: {}
  containers:
  - name: demo
    image: cloudnatived/demo:hello
    volumeMounts:
    - mountPath: /cache
      name: cache-volume
```
1. Declare the `emptyDir` Volume named `cache-volume`.
2. Mount it in the container at `/cache`.
3. Anything written to `/cache` goes to the Volume and is visible to other containers mounting it (all can read/write).

> **Warning:** Kubernetes does **not enforce file write locks**. Concurrent writes to the same file can corrupt data — implement your own locking or use a filesystem that supports it (`nfs`, `glusterfs`).

### 4.3 Persistent Volumes
- Databases need data to **outlive** the Pod.
- **Book's recommendation: don't start by running databases in Kubernetes** — prefer cloud-managed MySQL/PostgreSQL/NoSQL. Kubernetes is best at **stateless** apps; persistent data needs reliable, performant, secure, backed-up storage.
- If you must: use a **PersistentVolume (PV)** — details are provider-specific.
- **PersistentVolumeClaim (PVC)**: the most flexible way — a **request** for a type and size of storage (e.g. 10 GiB of fast read-write storage).

```yaml
volumes:
- name: data-volume
  persistentVolumeClaim:
    claimName: data-pvc
```

- Two ways to supply PVs:
    1. **Static**: pre-create a pool of PVs, claimed by PVCs.
    2. **Dynamic provisioning**: mounting a PVC automatically provisions and attaches suitable storage.
- StatefulSets can manage storage with a **`volumeClaimTemplate`** (auto-creates a PVC per replica).

| | **emptyDir** | **PersistentVolume (via PVC)** |
|:--|:--|:--|
| Lifetime | Only while the Pod runs on that node | As long as needed (independent of Pod) |
| Initial state | Starts empty | Provisioned storage of requested type/size |
| Stored | Node memory or disk | Storage backend (provider-specific) |
| Use cases | Cache, scratch, sharing files between containers | Databases, data that must survive |

## 5. Restart Policies
- Kubernetes **always restarts a Pod when it exits**, unless told otherwise.
- Set with `restartPolicy` in the Pod spec:

| Policy | Meaning |
|:--|:--|
| **`Always`** (default) | Restart the container whenever it exits |
| **`OnFailure`** | Restart only if it exited with a **non-zero** status (failure) |
| **`Never`** | Never restart |

```yaml
spec:
  restartPolicy: OnFailure
```
- To run a Pod **to completion** and stop, use a **Job** resource (see §12.5).

## 6. Image Pull Secrets
- Private registries need credentials.
- **Step 1:** store the registry credentials in a **Secret**.
- **Step 2:** reference it from the Pod with `imagePullSecrets`:

```yaml
spec:
  imagePullSecrets:
  - name: registry-creds
```

- You can also attach `imagePullSecrets` to a **service account** — every Pod using that account automatically gets the credentials.
- The exact credential data format is in the Kubernetes documentation.

## 7. Init Containers
- Run **before** the main application containers.
- Defined under `spec.initContainers`; mostly like normal containers, but:
    - they **do not use liveness/readiness probes**;
    - they must **run and exit successfully BEFORE** the other containers start.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo
spec:
  containers:
  - name: demo
    image: cloudnatived/demo:hello
  initContainers:
  - name: init-demo
    image: busybox
    command: ["sh", "-c", "echo Hello from initContainer"]
```

- Uses:
    - **pre-flight checks** before starting the app;
    - running a **bootstrap script** to prepare for the app;
    - common: **fetching Secrets from an external store** and mounting them into the app via a Volume before startup.
- **Caution: init containers must be idempotent** — safe to retry if run more than once.

## Part A — quick revision
- A Linux container = an **isolated set of processes** with ring-fenced resources; looks like a machine to itself.
- Containers are **not VMs**; each should run **one primary process**.
- A Pod usually has one main container + optional helpers.
- Image spec: `registry / namespace / repository : tag` — only the repository is required.
- Always specify a tag (**never rely on `latest`**); a **digest** gives truly deterministic deploys.
- Don't run as root → `runAsUser`; block root with `runAsNonRoot: true`.
- Also: `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`.
- Capabilities: drop all, add only what's needed.
- Containers in a Pod share data via a Volume; `emptyDir` dies with the Pod; PV/PVC persists.
- Init containers do setup before the app starts.

# PART B — MANAGING PODS

## 8. Labels

### 8.1 What are labels?
- **Key/value pairs attached to objects** (e.g. Pods) that specify **identifying attributes** meaningful to users, but **not to the core system**.
- In simple words: tags that are meaningful to *us*, not Kubernetes.
- Common use: label Pods with the application they belong to.

```yaml
metadata:
  labels:
    app: demo
```
- By itself a label has **no effect** (still useful as documentation). Its power comes from **selectors**.

### 8.2 Selectors
- A **selector** is an expression that matches a label (or set of labels) — a way to specify a group of resources.
- Example: a **Service** selector decides which Pods receive requests:

```yaml
spec:
  selector:
    app: demo
```
- Matches any Pod with `app: demo`. No `app` label, or a different value → **no match**.
- Labels also work directly with `kubectl` via `--selector` / `-l`:
    ```bash
    kubectl get pods --all-namespaces --selector app=demo
    kubectl get pods --show-labels
    ```

### 8.3 More advanced selectors
- **Equality** selectors (`app: demo`) are usually all you need.
- Combine labels with **AND** logic:
    ```bash
    kubectl get pods -l app=demo,environment=production
    ```
    ```yaml
    selector:
      app: demo
      environment: production
    ```
- **Equality selectors are the ONLY kind a Service supports.** Other kinds work in `kubectl` queries and richer resources (Deployments).

| Selector type | kubectl form | YAML form |
|:--|:--|:--|
| Equality | `kubectl get pods -l app=demo` | `selector: {app: demo}` |
| Inequality | `kubectl get pods -l app!=demo` (includes Pods with **no** `app` label) | — |
| Set: **In** | `kubectl get pods -l "environment in (staging, production)"` | `matchExpressions: [{key: environment, operator: In, values: [staging, production]}]` |
| Set: **NotIn** | `kubectl get pods -l "environment notin (production)"` | `matchExpressions: [{key: environment, operator: NotIn, values: [production]}]` |

### 8.4 Other uses for labels
- Any label can link Pods to Services (`app` is just the common one).
- **Separate environments in one cluster**: the Helm chart sets an `environment` label; the production Service selects **`app: demo` + `environment: production`** — without the second selector it would also match staging Pods.
- Slice and dice resources along many dimensions:
    ```yaml
    labels:
      app: demo
      tier: frontend
      environment: production
      version: v1.12.0
      role: primary
    ```
- **Canary deployments with labels**: two Deployments with `track: stable` and `track: canary`; a Service selecting only `app` sends traffic to **both**. Adjust replica counts to change the canary percentage; once done, relabel canary Pods as stable.

### 8.5 Labels vs annotations
| | **Labels** | **Annotations** |
|:--|:--|:--|
| Purpose | **Identify** resources; select groups | **Non-identifying** info used by tools/services outside Kubernetes |
| Example | `app: demo` | Helm hooks; ingress config (`kubernetes.io/ingress.class: alb`) |
| Restrictions | Tight (used in performance-critical internal queries) | Fewer restrictions |

**Label restrictions**
- Name ≤ **63 characters**; optional DNS-subdomain prefix ≤ **253 characters**, separated by `/`.
- Must **begin with an alphanumeric** character.
- May contain only alphanumerics, dashes, underscores and dots.
- Values are similarly restricted.
- In practice most labels are single words (`app`), so limits rarely matter.

## 9. Node Affinities
- Node affinity **steers Pods toward (or away from) nodes with certain properties**.
- Usually **not needed** — the scheduler is smart; if all nodes are equally suitable, don't bother.
- Exception: a Pod that is **expensive to restart** should avoid **preemptible** nodes (which can disappear without warning).
- Two types:
    - `requiredDuringSchedulingIgnoredDuringExecution` → **HARD** (rule must be met to schedule).
    - `preferredDuringSchedulingIgnoredDuringExecution` → **SOFT** (nice to have).

> **Key point:** the long names mean the rule applies **during scheduling, NOT during execution**. Once scheduled, the Pod **stays** even if the rule later stops being satisfied.

### 9.1 Hard affinity
- Express the kind of nodes you want using `nodeSelectorTerms`.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: "topology.kubernetes.io/zone"
            operator: In
            values: ["us-central1-a"]
```
- Only nodes in `us-central1-a` match → the Pod can only run there.

### 9.2 Soft affinity
- Same idea, but each rule has a **weight 1–100** that determines its relative influence.

```yaml
preferredDuringSchedulingIgnoredDuringExecution:
- weight: 10
  preference:
    matchExpressions:
    - key: "topology.kubernetes.io/zone"
      operator: In
      values: ["us-central1-a"]
- weight: 100
  preference:
    matchExpressions:
    - key: "topology.kubernetes.io/zone"
      operator: In
      values: ["us-central1-b"]
```
- The Pod can run anywhere, but nodes matching the **second** rule get **10× the priority** (weight 100 vs 10).

| | **Hard** (`required…`) | **Soft** (`preferred…`) |
|:--|:--|:--|
| Meaning | Rule must be met | Rule is a preference |
| If unmet | Pod **cannot be scheduled** | Pod is scheduled elsewhere |
| Weight? | No | Yes, **1–100** |
| Field | `nodeSelectorTerms` | `weight` + `preference` |

## 10. Pod Affinities and Anti-Affinities
- Node affinity uses **node properties**; Pod affinity bases scheduling on **what other Pods are already running on a node**.
- **Affinity (attract)**: Pods that work better together — e.g. web server + Redis cache — prefer the same node.
- **Anti-affinity (repel)**: Pods that should avoid each other — e.g. replicas of the same app should land on different nodes.
- Like node affinities, Pod affinities are **hard rules or soft weighted preferences**.

### 10.1 Keeping Pods together — `podAffinity`
Scenario: `app: server` and `app: cache` work on separate nodes but are faster on the same node (traffic never leaves the machine).

```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        labelSelector:
        - matchExpressions:
          - key: app
            operator: In
            values: ["cache"]
        topologyKey: kubernetes.io/hostname
```
- The server Pod is scheduled **only on a node that also runs a `cache` Pod**.
- If no such node exists, or it lacks resources, the Pod **cannot run**.
- `topologyKey: kubernetes.io/hostname` defines "same node" as same hostname.

> In real life this is often **not** what you want:
> - If they **must** be colocated → put the containers **in the same Pod**.
> - If colocation is merely preferable → use a **soft** Pod affinity.

### 10.2 Keeping Pods apart — `podAntiAffinity`

```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        labelSelector:
        - matchExpressions:
          - key: app
            operator: In
            values: ["server"]
        topologyKey: kubernetes.io/hostname
```
- Opposite sense: no `app: server` Pod may be scheduled on a node already running an `app: server` Pod.
- Enforces **even distribution** of server Pods — at the possible cost of not reaching the desired replica count.

### 10.3 Soft anti-affinity

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 1
      podAffinityTerm:
        labelSelector:
        - matchExpressions:
          - key: app
            operator: In
            values: ["server"]
        topologyKey: kubernetes.io/hostname
```
- Usually we care more about **enough replicas** than perfect distribution → make it **soft**.
- If it can be satisfied it will be; if not, the Pod is scheduled anyway. Weighted like soft node affinity.

### 10.4 When to use Pod affinities
- Treat them as **fine-tuning for special cases** — the scheduler already balances performance and availability.
- They **restrict the scheduler's freedom**, "trading one application for another".

| | **podAffinity** | **podAntiAffinity** |
|:--|:--|:--|
| Effect | Attracts Pods to nodes running matching Pods | Repels Pods from nodes running matching Pods |
| Example | Web server + cache on the same node | Spread replicas of the same app |
| Hard version | Pod may be unschedulable | Fewer replicas than desired |
| Soft version | Preferred colocation | Preferred spreading (**recommended for replicas**) |

## 11. Taints and Tolerations
- Node affinity is a **Pod property** that attracts/repels Pods to/from nodes.
- **Taints are the reverse**: a **node property that repels Pods**.
- Uses:
    - set aside nodes **reserved for specific Pods**;
    - Kubernetes **automatically taints** nodes with problems (low memory, no network);
    - mark nodes with **specialised hardware** (GPUs);
    - let certain Pods **tolerate** certain node problems.

### 11.1 Adding and removing taints
```bash
kubectl taint nodes docker-for-desktop dedicated=true:NoSchedule
kubectl describe node docker-for-desktop
kubectl taint nodes docker-for-desktop dedicated:NoSchedule-   # trailing minus removes
```
- `dedicated=true:NoSchedule` → no Pod can be scheduled there **unless it has a matching toleration**.
- Remove by repeating the command with a **trailing `-`** after the taint name.

### 11.2 Tolerations
Tolerations are **Pod properties** describing which taints they are compatible with.

```yaml
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```
- Meaning: "this Pod is allowed to run on nodes with taint `dedicated=true:NoSchedule`".
- Pods without the toleration **cannot** be scheduled there.
- If a Pod can't run because of taints → status **`Pending`**, and `describe` shows:
    ```
    Warning FailedScheduling ... 0/1 nodes are available:
    1 node(s) had taints that the pod didn't tolerate.
    ```
- **Node problems example:** if a node drops off the network, Kubernetes adds `node.kubernetes.io/unreachable`; normally the kubelet evicts all Pods. A Pod with a toleration for that taint can keep running in the hope the network returns.

| | **Affinity (node / Pod)** | **Taints & tolerations** |
|:--|:--|:--|
| Defined on | Pod spec | **Taint on node**, toleration on Pod |
| Direction | Pod **chooses** where to go | Node **repels** Pods unless tolerated |
| Typical use | Prefer zones / colocate / spread | Dedicated nodes, GPU nodes, node problems |
| Command | Written in Pod YAML | `kubectl taint nodes …` |

## 12. Pod Controllers

### 12.1 Why controllers?
Running a bare Pod is like `docker container run` — it works but is very limited:
- if the container exits, **you** must restart it;
- **one replica only**, no load balancing;
- you must pick nodes and keep the cluster balanced yourself;
- updates require stopping each image, pulling the new one and restarting.

**Controllers** automate all of this. The **ReplicaSet controller** maintains a specified number of replicas (starts new Pods if too few, kills extras if too many). A **Deployment** manages ReplicaSets to control rollouts: on update it creates a new ReplicaSet and eventually scales down the old one.

For most simple apps a **Deployment** is all you need. Other controllers: **DaemonSet, StatefulSet, Job, CronJob, HPA, Operators**.

### 12.2 DaemonSets
- Problem: send logs from every app to a central log server (ELK / Datadog).
- Options:
    - put logging code in **every app** → duplicated code, inefficient;
    - run a logging **sidecar** in every Pod → app stays clean, but several copies of the agent per node;
    - the agent just forwards logs, so **one copy per node** is enough → **DaemonSet**.
- A **daemon** is a long-running background process; a DaemonSet runs a daemon container on **each node**.
- Manifest looks like a Deployment:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd-elasticsearch
spec:
  template:
    spec:
      containers:
      - name: fluentd-elasticsearch
```
- Use a DaemonSet for **one Pod per node**. If a **fixed replica count** matters more than *which* node → use a **Deployment**.

### 12.3 StatefulSets
- Adds the ability to **start and stop Pods in a specific sequence** with **stable identities**.
- Deployment: Pods start/stop in **random order** and are interchangeable — fine for stateless services.
- StatefulSet: Pods are **numbered** (`redis-0`, `redis-1`, …) and started **in order**; this is needed by distributed apps (Redis, MongoDB, Cassandra) that elect a leader by a predictable name.
- `redis-0` becomes leader; later Pods join as replicas by contacting it.
- Ordering: each replica must be **running and ready** before the next starts; on termination, replicas shut down in **reverse order**, waiting for each.

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
spec:
  selector:
    matchLabels: {app: redis}
  serviceName: "redis"
  replicas: 3
  template:
    ...
```

- To address each Pod by DNS name, create a **headless Service** (`clusterIP: None`):
    - normal Service → one DNS entry (`redis`) load-balanced across Pods;
    - **headless** Service → the same name **plus per-Pod entries** (`redis-0`, `redis-1`, …).
- StatefulSets can manage storage with a **`volumeClaimTemplate`** that auto-creates a PVC per replica.

### 12.4 Jobs
- A Deployment runs N Pods **forever**; a **Job** runs Pod(s) a specified number of times and then **completes**.
- Ideal for batch processing and **queue workers** (start, do work, exit).
- Two fields:
    - `completions` — successful runs required before the Job is complete (default **1**);
    - `parallelism` — how many Pods run at once (default **1**).
- Queue-worker pattern: `parallelism: 10`, leave `completions` unset → 10 Pods consume the queue until it is empty, then exit.
- One-off task: both default to 1; a failed/crashed Pod is restarted; only **successful** exits count.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: queue-worker
spec:
  completions: 10
  template:
    spec:
      restartPolicy: OnFailure
      containers:
      ...
```
- Start manually (`kubectl apply` / Helm) or from automation (CD pipeline).
- Cleanup: **`ttlSecondsAfterFinished`** deletes the Job after N seconds; `0` deletes it immediately on completion.

### 12.5 CronJobs
- Like Unix cron (Greek *chronos* = time): runs a **Job periodically**.
- Two important fields:
    - `spec.schedule` — cron format (e.g. `"*/1 * * * *"` = every minute);
    - `spec.jobTemplate` — an ordinary Job template.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: demo-cron
spec:
  schedule: "*/1 * * * *"
  jobTemplate:
    spec:
      containers:
      ...
```

### 12.6 Horizontal Pod Autoscaler (HPA)
- A Deployment keeps a **fixed** replica count (adjustable manually); the **HPA adjusts replicas automatically** with demand.
- **Horizontal scaling** = change the number of replicas; **vertical scaling** = make each replica bigger/smaller (CPU/memory).
- The HPA watches a Deployment and a metric — most commonly **CPU utilisation as a % of the Pod's requested CPU**.
- Example, target **80%**:
    - mean usage **70%** → scale **down**;
    - mean usage **90%** → add replicas until the average falls.
- The size of the change is based on the **ratio of actual to target**: close → few replicas; far → larger adjustment.
- Needs the **Metrics Server**.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: demo-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: demo
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80
```
- Also supports built-in memory metrics and **custom app metrics** (error rate, requests per second).
- **Scheduled autoscaling (HPA + CronJob)**: if traffic is predictable (e.g. 20 Pods needed by 8 a.m.), a CronJob patches `minReplicas` up just before the spike and back down after — combined with cluster autoscaling this saves cost and ensures **capacity is ready** (scaling is not instant).

```yaml
args:
- "kubectl patch hpa service-hpa --patch {\"spec\":{\"minReplicas\":20}}"
```

### 12.7 Operators and CRDs
- Standard objects fit simple stateless apps; some apps need **multiple collaborating Pods initialised in order** (replicated databases, clustered services).
- **CRD (Custom Resource Definition)**: create **your own object types** — Kubernetes is extensible (e.g. Velero adds `Backup`, `Config`).
- Some CRDs only store data; others act as **Pod controllers**.
- **Operator** = a program that talks to the Kubernetes API and automates what a human operator would do for a complex app.
    - Step 1: create a CRD for the custom object.
    - Step 2: write the controller program.
- **OperatorHub.io** hosts hundreds of community Operators.

### 12.8 Controller comparison
| Controller | What it does | Use when |
|:--|:--|:--|
| **ReplicaSet** | Keeps a specified number of replica Pods running | Managed by Deployments (rarely direct) |
| **Deployment** | Manages ReplicaSets; **rolling updates** | Most simple stateless apps |
| **DaemonSet** | **One Pod copy on every node** | Logging agents, node-level daemons |
| **StatefulSet** | **Ordered, numbered** Pods; stable DNS; VolumeClaimTemplate | Clustered apps (Redis, MongoDB, Cassandra) |
| **Job** | Runs Pod(s) **to completion** (`completions`, `parallelism`) | Batch tasks, queue workers, one-offs |
| **CronJob** | Runs a Job on a **cron schedule** | Periodic tasks |
| **HPA** | **Auto-adjusts replicas** by metric | Variable load |
| **Operator + CRD** | Custom controller for complex apps | Replicated databases, clustered services |

## 13. Ingress
- **Services route internal traffic** (microservice → microservice).
- **Ingress routes external traffic into the cluster** to the right Service.
- Think of Ingress as a **load balancer** that works with a Service to get external requests to the right Pods (using label selectors).
- It all happens through an **Ingress controller**.

### 13.1 Ingress manifest

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
spec:
  rules:
  - http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: demo-service
            port:
              number: 8888
```
- Ingress looks at `demo-service`; that Service uses its **selector labels and readiness status** to choose a Pod.
- Pods that don't match, or that are **not Ready**, receive no requests.
- Beyond routing, Ingress can manage **SSL certificates**, **rate limiting** and other load-balancer features — depending on the controller.

### 13.2 Ingress controllers
- The controller implements Ingress resources; the choice depends on where the cluster runs and what features you need.
- Controller selection/configuration is usually done with **annotations**:

```yaml
kind: Ingress
metadata:
  name: demo-aws-ingress
  annotations:
    kubernetes.io/ingress.class: alb
    alb.ingress.kubernetes.io/scheme: internet-facing
```

- **Cloud-provider controllers** (book recommends starting here on a major cloud):
    - GKE/GCP → **Google Cloud Load Balancer Controller (GLBC)**
    - AWS → **AWS Load Balancer Controller**
    - Azure → **Application Gateway Ingress Controller (AGIC)**

| Controller | Notes |
|:--|:--|
| **nginx-ingress** | Community-maintained; NGINX has long been a popular load balancer |
| **NGINX Ingress Controller** | Backed by the NGINX company; different from the community project |
| **Contour** | Uses **Envoy** to proxy requests |
| **Traefik** | Lightweight; can also manage TLS certificates automatically |
| **Kong** | Plugin Hub: OAuth, LetsEncrypt, IP restriction, metrics |
| **HAProxy** | Long-popular load balancer; own Ingress controller + Helm chart |

### 13.3 Ingress rules — fanout
- Route by request URL to different backends (**fanout**):

```yaml
spec:
  rules:
  - http:
      paths:
      - path: /hello
        pathType: Prefix
        backend:
          service:
            name: hello
            port:
              number: 80
      - path: /goodbye
        pathType: Prefix
        backend:
          service:
            name: goodbye
            port:
              number: 80
```
- `/hello` → Service `hello`; `/goodbye` → Service `goodbye`.

### 13.4 Terminating TLS with Ingress
- Most controllers secure connections with **TLS** (formerly SSL) using a **Secret** containing the certificate and key, plus the `tls` section:

```yaml
spec:
  tls:
  - secretName: demo-tls-secret
  ...
---
apiVersion: v1
kind: Secret
type: kubernetes.io/tls
metadata:
  name: demo-tls-secret
data:
  tls.crt: LS0tLS1CRUdJTiBDRV...LS0tCg==
  tls.key: LS0tLS1CRUdJTiBSU0...LS0tCg==
```

### 13.5 cert-manager
- Automatically **requests and renews** TLS certificates from **Let's Encrypt** (or another ACME provider).
- Detects TLS Ingresses without a certificate and requests one; **auto-renews** before expiry.

## 14. Service Mesh
- Services + Ingress may be all you need, depending on organisational complexity; a **service mesh** is a newer, growing concept.
- A service mesh manages **complex network operations**:
    - **rate limiting**;
    - **encrypting traffic between microservices** (mTLS);
    - **metrics and logging** for requests — latency, tracing a request's path;
    - **automatic retries** of failed requests;
    - **blocking/denying** inbound or outbound requests.
- Advice: if you are just starting with a few apps, begin with **Service + Ingress**; adopt a mesh when you need its advanced capabilities.

| Service mesh | Key points |
|:--|:--|
| **Istio** | One of the first meshes; optional add-on in many hosted clusters (incl. GKE); can be self-installed |
| **Linkerd** | Many key features with a **lighter footprint** and less complexity; mTLS, request metrics, blue-green, retries |
| **Consul Connect** | HashiCorp; adds mesh capability to Consul — good for mixed environments (apps outside Kubernetes) |
| **NGINX Service Mesh** | Full mesh product using the **sidecar pattern**; mTLS, traffic splitting, network performance metrics |

> **Exam tip:** link the terms — the **sidecar pattern** (helper container beside the app) is used by service meshes and was introduced earlier for logging agents; **mTLS = mutual TLS**.

## Part B — quick revision
- **Labels** = key/value identity pairs; used with **selectors** to match groups.
- **Node affinities** attract/repel Pods to/from nodes with given attributes (e.g. zone); **hard** can block scheduling, **soft** are weighted suggestions (1–100).
- **Pod affinities** = prefer being scheduled with other Pods; **anti-affinities** repel (e.g. spread replicas).
- **Taints** mark nodes (dedicated hardware, node problems); Pods won't schedule there unless they have a **toleration**.
- **DaemonSet** = one Pod per node; **StatefulSet** = numbered, ordered Pods with predictable DNS (headless Service); **Job** = run to completion; **CronJob** = periodic; **HPA** = autoscale replicas.
- **CRDs** create custom objects; **Operators** implement orchestration for complex apps (OperatorHub.io).
- **Ingress** routes external requests by rule (URL), can terminate TLS; **cert-manager** automates certificates.
- **Istio, Linkerd, Consul Connect, NGINX Service Mesh** = service mesh tools for encryption, QoS, metrics, logging, complex routing.
